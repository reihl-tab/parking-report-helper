## Subject catalog read contract (verified 2026-11-08)

`GetSubjectCategories` is a read-only GET that returns the municipal subject
category tree. Provenance: the documented original capture in the private
106-app reference archive (the request that produced the 2026-10-05 snapshot),
confirmed by one bounded read-only request on 2026-11-08 (HTTP 200). No case
creation or other write was used to establish it.

- Method and path: `GET <BASE>GetSubjectCategories?token=<session token>`.
  The token is the 36-character GUID returned by `Login`, percent-encoded as a
  URL query value. Tokens in a JSON body are rejected (POST: 404, GET: 401);
  a `Token` header is rejected (401). Headers are the standard transport set:
  `Ocp-Apim-Subscription-Key`, `Content-Type: text/plain`, `User-Agent: App 106`.
- Response: a JSON array of category nodes. Node fields: `id` (GUID),
  `parentId`, `categoryName`, `categoryCode`, `level` (1-3),
  `parentCategoryCode`, `subjectCode` (null on pure grouping nodes), `icon`
  (base64 image), `children` (nested nodes), `categoryArabicName`, `order`.
- `Municipality.list_subject_categories` performs this GET; it validates the
  token and the response shape, caps the response size, refuses redirects and
  never logs the token, URL or response body.
- `parking_report.subjects.flatten_category_tree` converts the tree into rows
  of the captured-catalog shape (`code`, `name`, `path`), preserving repeated
  subject codes under different parents. `catalog_fingerprint` gives a stable
  secret-free hash over those rows, comparable between a live tree and the
  captured snapshot, so a refresh can detect municipal changes. On 2026-11-08
  the live catalog covered exactly the 72 codes and 86 subject rows of the
  2026-10-05 snapshot, with one whitespace-only name difference; the snapshot
  remains the catalog of record until a reviewed refresh replaces it.

## Private execution, public code

The reusable workflow runs in the CALLER's private repository, not in the public
repository. Never dispatch report data or secrets to public Actions. Pin both the
reusable workflow reference and `helper_sha` to the same reviewed full commit SHA.
Private pushes may invoke preview validation only. No public workflow handles data.
`api106.yml` restricts preview to one configured private caller repository via
an exact repository-name check. It is not an unrestricted reusable service;
changing that caller is a separate reviewed workflow change.

The private repo keeps `addresses.json`, report folders and originals. The provided
address dataset is not bundled in public code; its provenance/licensing is unknown.
Reporter variables are `PARKING_REPORTER_FIRST_NAME`, `LAST_NAME`, `PHONE`,
`ID_NUMBER`, `EMAIL` (each has the full `PARKING_REPORTER_` prefix).
They must be private secrets/environment values, never command-line literals.
API secrets are `PARKING_106_SUBSCRIPTION_KEY`, `PARKING_106_USERNAME` and
`PARKING_106_PASSWORD`. Preview requires no API credentials.
No real names, ID numbers, phone numbers or keys are in examples or fixtures.

## Local offline preview

```
python -m pip install --require-hashes -r requirements/build.txt -r requirements/api.txt
python -m pip install --no-deps --no-build-isolation .
parking-report-106 /private/reports/REPORT_FOLDER --addresses /private/addresses.json
```

Preview validates one ready intake record, builds Hebrew report text, resolves its
municipal street code, converts coordinates to ITM and prepares a resized JPEG with
EXIF removed. Street resolution normalizes spelling before matching: NFKC plus
folding the five Hebrew final letters onto their regular forms (#137), so a dataset
spelling like "ברוך" matches a record written "ברוכ"; ambiguous variants still
fail closed. A street entry may carry an optional "aliases" list of extra
accepted spellings (for example transliteration variants like רייך for רייק);
aliases pass through the same normalization and collide fail-closed (#139).
It emits only the digest, photo byte count and offline status.
No network calls or state writes happen. Inspect the original private record and
photo locally to review all details; logs are not a review of the full report.

## Explicit local submission gate

The reusable workflow's live job exits with an error instead of submitting;
`submit: true` does not enable live execution. The local engine is separate: it
requires `PARKING_106_ENABLE_LIVE=true`, `--submit` and `--approved-sha256` equal
to the reviewed preview digest. The digest binds reporter, payload and original
photo bytes. Gate approval does not itself prove identity or municipal permission.
Before any live execution review reporter, address, report text and photo together.
Omitted subject selection retains the `sidewalk_parking` live gate for 1145.
Other events use an explicit per-report owner choice and exact approved text;
see SUBJECTS.md for the captured catalog and unresolved mapping limits.
No secrets are printed. POSTs do not retry and redirects are refused.
Contact registration is a write, even before report creation.

## Durable ledger design for later live Actions enablement

The durable ledger implementation below covers these storage requirements.
The reusable workflow's live job remains disabled in the checked-in code.
The requirements below describe a separately reviewed enablement design, not a
claim about any private deployment's current status:

- The private workflow serializes all 106 jobs with a single concurrency group and
  `cancel-in-progress: false`; no other execution route may write the same ledger.
- Use a protected private environment for final approval and an explicit live flag.
  Approve one digest, not all records in a push. Submit only that frozen revision.
- Checkout the private ledger branch with write permission. Set
  `PARKING_STATE_GIT=1`, with `.106-state` unignored in the private repo. The runner
  commits and pushes every state transition before the next external effect.
- Reject stale checkouts; synchronize the ledger before selecting a report. Push
  failure blocks further work. Persist creating BEFORE CreateCase, created BEFORE
  attachment and complete AFTER confirmation. If a runner crashes after creation,
  the durable creating state blocks new creation until municipal reconciliation.
- A complete fingerprint returns the saved receipt without municipal requests.
  An uncertain creation is never retried. Failed attachments require checking the
  case first and explicit `--retry-photo`; attachment timeout can mean it succeeded.
- Altered inputs produce a different digest. Also keep a stable intake-record ID
  with the ledger to prevent edits from creating a second report for the same event.
  This stable-ID constraint is enforced by the private ledger; changed records are blocked.
- Ledger/receipts never become public artifacts. Use a private branch excluded from
  report-push triggers to prevent state commits from triggering new submissions.

Local state uses an exclusive lock, atomic replacement, fsync, 0700 directories
and 0600 files. Without Git mode it protects one persistent local computer only;
GitHub cache/artifact storage is NOT a reliable pre-request transaction ledger.
No automatic uncertain-result reconciliation is claimed.

## Stable IDs and durable ledger (implemented)

Use `--ledger-dir` pointing to a checked-out private `106-ledger` branch with
`ledger.json` initialized as `{"version":1,"reports":{},"photos":{}}`.
The report folder name is its stable ID. Renaming a folder with identical original
photo bytes is blocked by a global photo index. Changing a reserved folder's
payload, reporter or original photo is blocked and needs explicit reconciliation,
not a new ID or deleting state. Re-encoded/cropped photo copies are not detected
as the same original; keep original evidence and IDs intact. This is not a server
idempotency guarantee and cannot prevent unrelated manual submissions.

The runner holds an exclusive local lock across reservation and submission.
Private Actions uses one concurrency group for all 106 work. Every Git checkpoint
requires a clean checkout whose HEAD equals the remote ledger branch; commits
push without force, and remote acceptance is rechecked. Stale writers/rejected
pushes stop, not retry. Creating is durable BEFORE CreateCase; crash/timeout leaves
creating, which blocks automatic creation. Durable complete receipts are reused
from a fresh runner without municipal requests. Attachment retry still needs
manual reconciliation and an explicit request. Ledger checkpoints occur before
login/contact too. Live CLI requires this ledger, plus its existing exact digest,
private enablement and category gates. Live workflows remain disabled.

Offline previews can reserve stable IDs with no municipal requests. They publish
only hashes/state in the private branch, not reporter identity or report text.
The legacy PARKING_STATE_GIT hook is unnecessary with `--ledger-dir`; do not set
both. Never use GitHub caches/artifacts as the pre-request transaction log.
Local fake-Git-remote tests exercise new runners, stale writers, failed pushes,
changed IDs/photo reuse, uncertain creation and durable receipt reuse.

## Sanctioned corrected re-filing (supersedes)

Issue #260. The photo guard allows one intake ID per original photo. When an
owner asks for a corrected case on the same evidence photo while the first
case is still open (for example the street was wrong), the new intake's
private `report.json` may carry `supersedes` with exactly `parent_id`,
`parent_digest` and `approval_reference`. There is no case number and no
closure time: the parent may be uncased and open. Unknown or missing fields,
a `parent_id` equal to the intake's own folder name, and a combination with
`followup`, `shared_photo` or `shared_photo_extension` are refused. A
manifest is an audit record, never permission by itself.

The whole manifest and the new intake ID are bound into the preview digest.
A live run also needs `--approved-supersedes-sha256` equal to that digest, as
well as every normal gate (`PARKING_106_ENABLE_LIVE=true`, the exact
`--approved-sha256` and `--ledger-dir`). Supersedes previews never reserve a
ledger slot, even with `--ledger-dir`. A corrected payload that, without its
manifest, still has the parent's digest is refused as an exact duplicate.

The durable ledger reserves the child only when the parent entry exists, has
the manifest's `parent_digest` and the same original photo, is an ordinary
intake (no follow-up, shared-photo or extension relation), has not been
superseded already, and is in one of the open ledger states `prepared`,
`creating`, `created`, `attaching` or `complete`; any other or missing state
fails closed. A child digest equal to the parent's is refused. The child is
then permitted the parent's photo under its own intake ID and carries
`supersedes`; the parent gains only `superseded_by: <child intake ID>`, in the
same ledger commit. The parent's digest, state and case number and the
original photo index stay unchanged, so ordinary duplicate photos remain
blocked. Nothing retracts or edits the parent case at the municipality.
